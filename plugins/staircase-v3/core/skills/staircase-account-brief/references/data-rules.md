# Data rules and field guide

What the tool descriptions and recipes do not say. Each rule names the server gap it covers; delete a rule when the server closes its gap. What the tool descriptions already cover (picklist option ids, case-sensitive Equal, the default metric window, pagination keys, child aggregations, scalar COUNT shape) is not repeated: read the tool description.

## Dates (read first)

Every window anchors on **the user's local today**: the date the conversation gives, or the local clock when a tool can read it. Never the server's UTC date. Each window below is exactly N days, both ends included:

| The user says | Pass | Example, local today 2 Nov |
|---|---|---|
| "next N days" | `["<today>", "<today + N - 1>"]` | next 90 days: `["2026-11-02", "2027-01-30"]` |
| "last N days", "past N days" | `["<today - N + 1>", "<today>"]` | last 30 days: `["2026-10-04", "2026-11-02"]` |
| "no touch in N days" | `customer.last_touch` LessThan `<today - N + 1>T00:00:00Z`, Or `customer.last_touch` NotDefined | no touch in 30 days: LessThan `2026-10-04T00:00:00Z` |
| "this quarter", "Q3", "next fiscal year" | Explicit dates from `fiscal_year_start_month` (`company-profile.md`); if not set, calendar quarters, labeled "calendar quarter (default)" | |

Compute the dates with a tool when one runs, and print both in the answer ("2 Nov to 30 Jan, both included"). Use the arrays in InRange filters on date fields and in metric `dateRange` arguments alike. A named window (`[Next90Days]`, `[PastMonth]`) is a fallback only when no date can be computed: print it by name and say its bounds are the server's.

**Times.** Row dates, `meeting.start_time` and `customer.event.next_event` are UTC. Show them in the user's local zone with the offset in force on that date (else UTC, and say so once): a late-evening meeting can carry the next day's UTC date.

## Rules

| # | Rule | Server gap |
|---|---|---|
| 1 | Set top-level `arguments.dateRange` on every report rooted on `lifecycle_event`, `meeting` or `feedback`, and state the window. An InRange filter on the date alone is still clamped | These roots silently return only the last 14 days. The churn recipe advises an InRange filter instead of `arguments.dateRange`; follow this rule there |
| 2 | Churn by product: top-level `arguments.productId` works on `lifecycle_event` reports. Still print the share of events that carry a product tag | The churn recipe says productId is rejected; that text is stale |
| 3 | Churn counts include the Churn Status event (`churn_status`: churned accounts where no notice was heard) beside `churn` and `churn_risk`. In another tenant, confirm the id in metadata | The churn recipe predates it |
| 4 | One `dateRange` per metric per call; the same metric over two windows goes in two calls | Builds time out with no hint |
| 5 | A customer report can time out (`code: timeout`, or `invalid_config` saying it takes too long). Never resend the same config: split it in half once, join on `customer.id`, and say so. Keep book pulls narrow from the start (`action-priority.md`) | 60-second build limit, no "fewer columns" hint |
| 6 | Group-by rollups (rooted on `tier`, `user` and so on) leave out rows whose group is blank. Reconcile with a scalar COUNT on the same filter and print the remainder ("no tier: N") | No `groupBy`; blank groups drop silently |
| 7 | Staleness goes in the filter, never in your arithmetic, with the "no touch" form in Dates above. Count never-touched accounts (NotDefined) in the total, and show them as their own line | Recipes say "do not count days" but not how; NotDefined rows drop out of a before-date filter |
| 8 | `customer.last_touch` can sit in the future; treat it as now | Undocumented |
| 9 | A comparison on a sparse field drops blanks ("risk LessThan 4" leaves out unassessed accounts). Add an Or with NotDefined when blanks belong in the set | Null handling undocumented |
| 10 | Null booleans: "not set" is NotEqual true, never Equal false | Null and false differ silently |
| 11 | Open-thread counts for a waiting-customer check: the last 30 days, as an explicit array (Dates above) | The two-week default misses older waits |
| 12 | `customer.last_lifecycle_event_date` looks back 365 days at most | Undocumented |
| 13 | `commType` on customer fields is accepted and ignored. Split channels with the per-channel fields (`customer.email.*`, `customer.event.*`, `customer.message.*`, `customer.ticket.*`) | Silent no-op |
| 14 | `aggregateParentChild` with `filter.user` or `productId` is rejected; leave it false | Error text only |
| 15 | Next meeting: `customer.event.next_event`. `meeting.is_scheduled` is true for past meetings too | Misleading field |
| 16 | Never sort or page on an id. Customer reports: one unsorted page (up to 1,000 rows) or `customer.name` as the last sort key, deduped by `customer.id`, the total checked with a scalar COUNT (rule 22). Lifecycle events: sort by the event date, then dedupe by event id | Sorts on `customer.id` and `lifecycle_event.id` are silently ignored, so offset paging on them drops or repeats rows with no error |
| 17 | `staircase_list_communications`: set `per_account_limit` (default 25 rows per account, at most 100) and `limit` (default 100 rows for the whole call, across accounts) on every call; `limit` = accounts x `per_account_limit`, at most 300, so batch the accounts (3 a call at 100 rows each, 6 at 50, 30 at 10) and run as many calls as the scope needs. An account that comes back at its cap gets the earlier-window call below before any item on it is judged; otherwise say "unconfirmed: older rows not read". `truncated`, `has_more` and `complete: false` come from these caps (and `per_event_limit` on event calls): print threads read out of `total_count`. A row's date is its thread's latest message, so rows can fall after the window end and windows overlap: to read further back, end the next window the day before the oldest row's date and dedupe by `evidence_id`. One conversation can split across two evidence ids (a reply that started a new thread): check same-subject rows before saying who wrote last | Silent defaults of 25 rows per account and 100 per call; no page cursor; rows carry no subject or conversation id |
| 18 | Metadata once per session. Never paste, list or summarize it into an answer | About 100k characters |
| 19 | Never use `staircase_analyze_account` (being removed) or `staircase_generate_report` (gone). One account's story runs on `single_account_analysis` | Both still appear in some tool lists |
| 20 | Never hardcode a tenant's role fields, custom fields, tiers, insight or event types, or product ids. Take them from metadata, a report or `company-profile.md`, and say when one is absent | Tenant-specific |
| 21 | Windows follow the Dates section: the user's local today, exactly N days, explicit arrays, dates printed | Named windows resolve on the server's UTC date, exclude their end, never echo their bounds, and roll at UTC midnight. Renewals cluster at month end: one rollover moved a 90-day renewal count by about 15 percent |
| 22 | On a paged report, the last page can read `complete: false` with `has_more: false`. Confirm the total with a scalar COUNT | Undocumented flag pair |
| 23 | A child COUNT of `lifecycle_event` rows (under a `customer`, `tier` or `lifecycle_event_type` root) is not clamped to 14 days: with no date in its child `condition` it counts all history. Put the window in the child condition (InRange on `lifecycle_event.date`, dates per the Dates section). A signal audit by type is then one call | The 14-day clamp applies to event roots only; child counts silently span all time |
| 24 | A stopped ticket feed (`evidence.md`, freshness) biases every topic growth figure and ticket trend: across the stop, pass `commType` without Ticket on topic metrics, or end both windows on the last ticket date for a ticket-only ask, and say so | One stop read a theme at -23 percent with tickets and -9 percent without; the sync flag stays healthy |
| 25 | A renewal date more than 30 days past on an Active account is a stale date, likely a CRM date never moved after the renewal closed. Never rank it as a renewal decision or as renewal nearness; list it in one record-check line ("ask whether it closed and the date moved"). A date passed in the last 30 days is a live decision | CRM renewal dates lag closed renewals (1 to 16 months past in one team); no renewal outcome record |

## Field guide (standard fields; check each id against metadata before use)

| Job | Field ids | What it means |
|---|---|---|
| Identity | `customer.id` (a number: always add `customer.name`; never sort on it, rule 16), `customer.status`, `customer.renewal_date` (a Date), `customer.revenue_converted`, `customer.url` (the account's page, for notes to an admin) | Status, tier, renewal date and revenue come from the CRM and can be blank. The CRM is authoritative for contract figures. One renewal date can cover several products whose terms differ |
| Tier | `customer.tier`, a Reference to the `tier` entity (`tier.id`, `tier.name`) | Metadata lists no tier options: get ids from a `tier` report. Filter `customer.tier` In [`tier.id` values], or `customer.tier.name` Contains a name the user gives |
| Scores | `customer.buckets.health_score`, `customer.buckets.sentiment.numeric_score`, `customer.buckets.engagement.*`, `customer.buckets.open_items.numeric_score` | 0 to 100, current values only (no history). Open items: higher means fewer open items than peers. A health score of 0 means no data, and its label then reads Low |
| AI levels and narratives | `customer.risk.risk_level`, `customer.expansion.readiness_level` (Numbers, 1 to 5: "risk 4 or 5" is GreaterOrEqual 4); `customer.risk.analysis`, `customer.churn.synopsis`, `customer.renewal.synopsis`; `customer.handoff.*` (handoff summary and objectives) | Present only when assessed; blank means not assessed. Readiness skews high. A stored narrative can run ahead of status (a past-tense churn analysis on an Active account) or describe another product: quote it as stored, with the status beside it. Refresh dates exist for expansion and handoff (`customer.expansion.last_refreshed_at`, `customer.handoff.last_refreshed_at`), none for risk |
| Touch | `customer.last_touch` (our side), `customer.last_engagement` (customer side: email, ticket, meeting attended), `customer.last_reach_out`, `customer.last_dm_touch`, `customer.email.customer_last_sent`, `customer.email.organization_last_sent` | DateTime, UTC. `organization_last_sent` counts any colleague. Automated mailboxes count as touch. `last_dm_touch` counts only contacts tagged as decision makers: blank can mean none is tagged, and an old date beside senior contacts on recent calls points to tagging, not touch |
| Waiting | `customer.email.customer_open_threads` (likely waiting on us), `customer.email.organization_open_threads` (likely waiting on them) | Email only; solicitations count. Direction is inferred from code (one table unread) and not confirmed live: read the thread's last message before saying who owes a reply |
| Meetings | `customer.event.last_event`, `customer.event.next_event`, `customer.event.count`; the `meeting` root (`meeting.summary` as subject, `start_time`, `organizer.email`, `has_recording` labeled Has Transcript); `stakeholder.event_stats.next_scheduled_event` | `next_event` is the simplest "next meeting": account-wide, the first meeting only, and often a mass invite, so it cannot carry urgency on its own. The `meeting` root returns future meetings once a forward `arguments.dateRange` is set (rule 1), with no attendees. A meeting without a transcript appears in no communication tool. `customer.event.count` under `filter.user` can count invitations, not attendance. Contacts whose `next_scheduled_event` falls InRange the meeting date are its likely invitees |
| One person's engagement | `customer.email.sent_count`, `customer.email.organization_sent_count`, `customer.email.customer_sent_count`, `customer.event.count`, each with `filter.user` | See `scope.md`. Never `customer.total_activity` for a person |
| Events | `lifecycle_event` (`type`, `date`, `customer`); `customer.last_lifecycle_event_date` with `eventType` | Common type ids: `churn` (a notification, not an outcome), `churn_risk`, `churn_status` (churned with no notice heard), `farewell` (a personnel change), `organization_personnel_change` (our side), `exceptional_negative`, `exceptional_positive`, `renewal_discussion`, `renewal` (fires after a renewal). Tenants add types; labels differ from ids. A label and its thread can disagree, so read before relying on one: `farewell` ("Account personnel changes") also fires on our side, on leave and on joiners; `renewal_discussion` ("Commercial discussion") also fires on expansion, pilot and new-product threads; a written non-renewal can be typed `churn_risk`; `renewal` events can have no linked communication (count them, never call one a win). Event rows carry no subject or sender |
| Insights | `customer.insight_detected` with `insightType`; the `insight` entity (current state, undated) | Common: ChurnRisk, Farewell, CustomerDark, NoRenewalDiscussion, NoNextMeeting. Some read zero everywhere: check the base rate |
| Expansion rows | `expansion_opportunity` (offering, category, confidence_level, momentum_state, decision_maker, budget_status, timeline_indicator) | One row per account and offering. Budget and value are free text: never sum |
| Stakeholders | `stakeholder` (name, email, title, role, type, `last_engagement`, `last_reach_out`), `stakeholder_role` | Roles are tenant labels; many read Unknown. Filter `type` In [Human] and recent engagement: unfiltered, a few accounts fill a page with inactive people. The only source of contact email addresses |
| Topics | `parent_topic`, `child_topic` (`parentTopicId`, `accounts_count`, `total_count`, `negative_sentiment`, `previous_period_volume`, `absolute_growth_percentage`, each with `filter.customer`); `customer.topic_communication.total_activity` and the per-channel `customer.topic_communication.email.sent_count`, `.video.total_count`, `.chat.total_count`, `.ticket.total_count` (`topicId`) | Find topic ids by name each run (`argument_options.topicId`); tenants add parent topics. `topicId` takes a parent or a child id and must be a number (the search schema says string; a string is rejected), so a child theme's accounts, renewals and revenue share are exact scalars. `total_activity` takes no `commType`: split channels with an `Or` of the per-channel metrics. Growth fields compare the window with the equal-length window just before it; growth reads 0 when the prior is 0 (new) and -1 when the current is 0. Without `filter.customer`, a topic metric counts every account in the tenant, prospects included |
| Product feedback | The Feature requests parent topic and its child topics, plus `staircase_semantic_search` | Never the `feedback` entity: it holds users' corrections to Staircase AI output, not customer product feedback |
| Tickets | `customer.ticket.last_opened`, `customer.ticket.submitted_count` | No ticket entity (no status or priority). Check freshness first, org-wide (`evidence.md`) |
| Team | `user.manager`, the `manager` entity (whole hierarchy), `customer.<role_field>.full_name` | No pooled-user flag |
